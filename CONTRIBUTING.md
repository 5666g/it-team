# Руководство по внесению изменений (Contributing Guidelines)

Мы рады приветствовать вас в качестве участника проекта **IT Team**!  
Чтобы командная разработка проходила слаженно, прозрачно и без конфликтов, пожалуйста, соблюдайте изложенные ниже правила.

---

## 📌 Основные правила командной работы

1. **Работа строго через личный Fork:**  
   Прямая отправка изменений (`git push`) в ветку `main` оригинального репозитория запрещена настройками прав доступа. Все изменения поступают исключительно через механизм **Fork & Pull Request**.
2. **Одна задача — одна ветка:**  
   Никогда не делайте коммиты напрямую в ветку `main` собственного форка. Всегда создавайте изолированную ветку (`feature branch`) под вашу страницу.
3. **Редактируйте только свой назначенный файл:**  
   Каждому студенту назначается строго один файл в папке `pages/`.  
   *Не изменяйте файлы `index.html`, `style.css` или страницы других участников без явного согласования с преподавателем.*
4. **Не добавляйте персональные конфиденциальные данные:**  
   Категорически запрещено публиковать личные номера телефонов, пароли, токены доступа или паспортные данные. Все контакты должны быть условными или учебными.

---

## 🌿 Соглашение по именованию веток

Имя ветки должно отражать суть выполняемой задачи и начинаться с префикса `feature/`:

* Студент 1 (Команда): `feature/team-members`
* Студент 2 (Проекты): `feature/projects-list`
* Студент 3 (Технологии): `feature/technologies-stack`
* Студент 4 (О команде): `feature/about-us`
* Студент 5 (Контакты): `feature/contacts-info`
* Студент 6 (Достижения): `feature/achievements-list`
* Студент 7 (Мероприятия): `feature/events-schedule`
* Студент 8 (Ресурсы): `feature/learning-resources`

## 💬 Соглашение по оформлению сообщений коммитов

Мы придерживаемся формата [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>: <краткое описание на русском или английском языке>
```

### Рекомендуемые типы:
* `feat:` — добавление новой страницы, новой секции или карточек контента.
* `fix:` — исправление опечатки, поломанного тега или неверной ссылки.
* `docs:` — исправление документации или комментариев в коде.

### Примеры хороших коммитов:
* `feat: добавить карточки участников команды`
* `feat: наполнить раздел проектов и технологий`
* `fix: исправить закрывающий тег article в pages/team.html`

### Примеры плохих коммитов:
* `commit` *(неинформативно)*
* `asdfgh` *(бессмысленно)*
* `сделал работу` *(непонятно, что конкретно изменено)*

## 🔍 Требования к Pull Request (PR)

Перед отправкой Pull Request убедитесь, что:
1. Вы открыли локальный HTML-файл в браузере и визуально проверили его внешний вид.
2. В выводе команды `git status` изменён **только ваш HTML-файл**.
3. В заголовке PR указан номер задания и краткая суть, например:  
   `feat: Наполнение страницы участников команды (Студент 1)`.
4. В описании PR кратко перечислено, что было сделано:
   ```markdown
   ### Что сделано:
   - Удалён блок-заглушка `.stub-box`.
   - Добавлены 3 карточки участников с ролями и тегами.
   - Проверена адаптивность в мобильном режиме.
   ```
5. В интерфейсе GitHub правильно выбраны репозитории:
   - `base repository`: `ПРЕПОДАВАТЕЛЬ/it-team` (ветка `main`);
   - `head repository`: `ВАШ_ЛОГИН/it-team` (ваша ветка `feature/...`).

## 🔄 Реагирование на замечания ревьюера

Если преподаватель запросил исправления (**Request changes**):
1. Не закрывайте PR!
2. Внесите изменения в файл на своём компьютере.
3. Сделайте новый коммит: `git commit -am "fix: устранить замечания по разметке"`.
4. Отправьте коммит в свой форк: `git push`.
5. GitHub автоматически добавит новый коммит в открытый PR, после чего преподаватель выполнит слияние (**Merge**).
