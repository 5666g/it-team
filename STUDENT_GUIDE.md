# Пошаговое руководство для студента: Работа с Git и GitHub

Добро пожаловать в проект **IT Team**! В рамках этой лабораторной работы вы пройдёте весь путь разработчика в открытом проекте: от форка репозитория до создания собственного Pull Request и его слияния в основную ветку.

---

## 📌 Ключевые понятия перед началом

Прежде чем приступать к командам в терминале, разберёмся с основными понятиями.

### 1. Что такое Fork и зачем он нужен?
* **Fork (форк)** — это копия чужого репозитория, создаваемая внутри вашей личной учётной записи GitHub.
* В профессиональной разработке и мире Open Source у обычных разработчиков нет прав прямой записи (`push`) в оригинальный репозиторий проекта.
* Fork даёт вам полную свободу: вы можете вносить любые изменения в свою копию, не рискуя сломать основной проект.

### 2. Почему мы работаем в личном Fork, а не напрямую?
* Если бы все 8 студентов одновременно отправляли коммиты в одну и ту же ветку `main` оригинального репозитория, возникли бы постоянные конфликты версий и хаос.
* Работая через Fork, каждый студент трудится в изолированном пространстве. Готовый результат отправляется автору оригинального проекта на проверку через **Pull Request**.

### 3. Что такое Clone?
* **Clone (клонирование)** — это загрузка копии репозитория с сервера GitHub на ваш локальный компьютер.
* После клонирования на вашем диске появляется папка с файлами проекта и полной историей изменений Git.

### 4. Чем `origin` отличается от `upstream`?
Когда вы работаете с форком, у вас появляются две удалённые связи (remotes):
* **`origin`** — это адрес **вашего личного форка** на GitHub (сюда вы имеете право делать `git push`).
* **`upstream`** — это адрес **оригинального репозитория преподавателя** (оттуда вы подтягиваете свежие обновления и изменения одногруппников).

```text
[Оригинальный репозиторий преподавателя]  <-- upstream (только чтение для вас)
                  │
                  ▼ (Fork на GitHub)
[Ваш личный форк на GitHub]               <-- origin (чтение и запись)
                  │
                  ▼ (git clone)
[Локальная папка на вашем компьютере]      <-- local workspace
```

### 5. Что такое GitHub Issues и зачем они нужны?
* **Issue (задача / тикет / баг-репорт)** — это встроенная система трекинга задач внутри каждого репозитория на GitHub.
* В профессиональной разработке ни одна строчка кода не пишется «просто так». Любая задача, идея или обнаруженная ошибка сначала оформляется в виде **Issue**:
  - Там фиксируется подробное техническое задание (ТЗ) и список требований.
  - Назначается ответственный исполнитель (**Assignee**).
  - Навешиваются метки (**Labels**), например `lab-task`, `student-1`, `bug` или `enhancement`.
  - Оформляется интерактивный чек-лист готовности (**Definition of Done**).
* **Связка Issue & Pull Request:** когда вы отправляете Pull Request, вы решаете конкретную Issue. Указав в описании PR волшебную фразу (например, `Closes #1`), вы автоматически закроете задачу, как только преподаватель нажмёт кнопку **Merge**!

## 🚀 Пошаговый алгоритм выполнения работы

### Шаг 0. Поиск своей задачи во вкладке Issues
Перед тем как писать команды в консоли, найдите свою персональную карточку задачи на GitHub:
1. Откройте оригинальный репозиторий преподавателя: `https://github.com/ИМЯ_ПРЕПОДАВАТЕЛЯ/it-team`.
2. Перейдите во вкладку **Issues** (Задачи).
3. Найдите тикет с вашим номером задачи (например: `[Task 1] Заполнение страницы участников команды (pages/team.html)`).
4. Откройте задачу и внимательно изучите:
   - **Номер задачи** (например, `#1` или `#2`) — он понадобится при создании Pull Request!
   - **Файл**, который вам назначен (`pages/team.html`);
   - **Рекомендуемое имя ветки** (`feature/team-members`);
   - **Критерии готовности** (чек-бокс список Definition of Done).
5. Нажмите внизу поле комментариев и напишите: `Беру в работу!` — чтобы преподаватель и одногруппники видели, кто занят этой задачей.

---

### Шаг 1. Создание Fork на GitHub
1. Откройте в браузере страницу оригинального репозитория преподавателя:
   `https://github.com/ИМЯ_ПРЕПОДАВАТЕЛЯ/it-team`
2. В правом верхнем углу страницы найдите и нажмите кнопку **Fork**.
3. В появившемся окне оставьте название репозитория без изменений и нажмите зелёную кнопку **Create fork**.
4. Через 2-3 секунды GitHub перенаправит вас на страницу вашей копии:
   `https://github.com/ВАШ_ЛОГИН/it-team`.

---

### Шаг 2. Клонирование собственного Fork
1. На странице **вашего форка** нажмите зелёную кнопку **Code**.
2. Скопируйте ссылку (HTTPS): `https://github.com/ВАШ_ЛОГИН/it-team.git`.
3. Откройте терминал (Git Bash, терминал VS Code, macOS Terminal или PowerShell) и перейдите в папку, куда хотите сохранить проект:
   ```bash
   cd ~/Documents
   ```
4. Выполните команду клонирования:
   ```bash
   git clone https://github.com/ВАШ_ЛОГИН/it-team.git
   ```
5. Перейдите в скачанную папку репозитория:
   ```bash
   cd it-team
   ```

---

### Шаг 3. Добавление связи с оригинальным репозиторием (upstream)
Чтобы ваша локальная копия знала об основном репозитории преподавателя, настройте связь `upstream`:

```bash
git remote add upstream https://github.com/rillside/it-team.git
```

Проверьте список удалённых репозиториев:
```bash
git remote -v
```
Вы должны увидеть 4 строки (две для `origin` и две для `upstream`):
```text
origin    https://github.com/ВАШ_ЛОГИН/it-team.git (fetch)
origin    https://github.com/ВАШ_ЛОГИН/it-team.git (push)
upstream  https://github.com/ИМЯ_ПРЕПОДАВАТЕЛЯ/it-team.git (fetch)
upstream  https://github.com/ИМЯ_ПРЕПОДАВАТЕЛЯ/it-team.git (push)
```

---

### Шаг 4. Создание отдельной рабочей ветки
Никогда не делайте изменения напрямую в ветке `main`! Для каждой новой функциональности создаётся отдельная ветка (`feature branch`).

Узнайте имя ветки для вашей задачи (см. таблицу внизу или файл `ISSUES.md`).
Создайте ветку и сразу переключитесь на неё:

```bash
# Пример для Студента 1:
git checkout -b feature/team-members

# Или современная альтернатива:
# git switch -c feature/team-members
```

Убедитесь, что вы находитесь в созданной ветке:
```bash
git branch
```
*(Текущая ветка будет отмечена звёздочкой `*`)*.

---

### Шаг 5. Открытие проекта в редакторе кода
Откройте всю папку проекта `it-team` в редакторе (рекомендуется **Visual Studio Code**):

В проводнике слева вы увидите структуру:
* `index.html` — главная страница (её редактировать не нужно!);
* `style.css` — стили (редактировать не нужно!);
* `pages/template.html` — шаблон для копирования блоков;
* `pages/<ваша-страница>.html` — файл, назначенный именно вам.

---

### Шаг 6. Наполнение назначенной страницы
1. Откройте файл `pages/template.html`. Посмотрите, как устроены карточки `<article class="card">` и списки `<ul class="custom-list">`.
2. Откройте **ваш файл** (например, `pages/team.html`).
3. Найдите в нём блок с заглушкой `<div class="stub-box">...</div>`.
4. Замените блок заглушки на карточки с реальной информацией по вашей теме (или раскомментируйте готовый пример под заглушкой и измените текст).
5. **Важные правила для сохранения вёрстки:**
   - Не удаляйте теги `<header>`, `<main>`, `<div class="container">`, `<footer>`.
   - Не меняйте ссылки в меню навигации.
   - Заменяйте только тексты внутри заголовков `<h3>`, абзацев `<p>` и бейджей `<span>`.

---

### Шаг 7. Проверка результата в браузере
Перед созданием коммита обязательно посмотрите, как выглядит страница:
1. Найдите ваш изменённый файл на компьютере и откройте его двойным щелчком в браузере (Google Chrome, Firefox, Яндекс.Браузер, Safari или Edge).
2. Либо в VS Code нажмите правой кнопкой мыши на файл и выберите **Open with Live Server** (если установлено расширение) или скопируйте путь к файлу.
3. Убедитесь, что:
   - Все тексты отображаются красиво.
   - Стили подключены корректно (фон тёмный, карточки с фиолетовыми акцентами).
   - Ссылки в меню работают и возвращают на главную страницу (`../index.html`).

---

### Шаг 8. Проверка изменений в Git (`status` и `diff`)
Вернитесь в терминал и проверьте, какие файлы были изменены:

```bash
git status
```
*Вы должны увидеть в красном цвете только один ваш файл, например `modified: pages/team.html`.*

Посмотрите точные построчные изменения:
```bash
git diff
```
*(Зелёным цветом помечены добавленные строки, красным — удалённые. Для выхода из режима просмотра нажмите клавишу `q`).*

---

### Шаг 9. Добавление изменений и создание коммита
1. Подготовьте файл к фиксации:
   ```bash
   git add pages/team.html
   ```
2. Создайте коммит с понятным описанием на русском или английском языке:
   ```bash
   git commit -m "feat: добавить карточки участников команды"
   ```

---

### Шаг 10. Отправка ветки в собственный Fork (`git push`)
Отправьте созданную ветку в ваш удалённый репозиторий на GitHub (`origin`):

```bash
git push -u origin feature/team-members
```
*(Замените `feature/team-members` на точное имя вашей ветки).*

Флаг `-u` связывает вашу локальную ветку с веткой на GitHub, чтобы в дальнейшем можно было просто писать `git push`.

---

### Шаг 11. Создание Pull Request (PR)
> **Очень важно понимать:** Команда `git push` не переносит код в репозиторий преподавателя автоматически! Она лишь загрузила ветку в ваш личный форк. Чтобы предложить свои изменения преподавателю, нужно открыть **Pull Request**.

1. Откройте в браузере страницу **вашего форка** на GitHub (`https://github.com/ВАШ_ЛОГИН/it-team`).
2. Вверху появится жёлтая плашка с кнопкой **Compare & pull request**. Нажмите её.
3. Если плашка не появилась, перейдите во вкладку **Pull requests** и нажмите **New pull request**.
4. **ВНИМАТЕЛЬНО проверьте направление слияния (4 выпадающих списка):**
   * **base repository**: `rillside/it-team` (куда вы отправляете)
   * **base**: `main/master`
   * **head repository**: `ВАШ_ЛОГИН/it-team` (откуда вы берете)
   * **compare**: `feature/team-members` (ваша рабочая ветка)
5. Укажите понятный заголовок: `feat: Заполнение страницы участников команды (Студент 1)`.
6. В описании обязательно **привяжите задачу из Issues** с помощью ключевого слова `Closes #номер` (или `Fixes #номер`):
   ```markdown
   Closes #1

   ### Выполнено задание №1:
   - Заменена заглушка в файле pages/team.html
   - Добавлены 3 карточки с участниками команды
   - Проверена адаптивность и ссылки
   ```
   > 💡 **Магия GitHub:** благодаря строке `Closes #1` (укажите номер своей Issue), когда преподаватель проверит ваш код и нажмёт кнопку **Merge**, ваша задача во вкладке Issues автоматически закроется со статусом **Closed**!
7. Нажмите зелёную кнопку **Create pull request**.

---

### Шаг 12. Ответ на замечания и обновление Pull Request
После создания PR преподаватель проверит ваш код.

Если преподаватель оставил комментарий и попросил исправить опечатку или тег:
1. **НЕ нужно закрывать старый Pull Request и создавать новый!**
2. Откройте файл в редакторе, внесите исправления и сохраните файл.
3. В терминале выполните:
   ```bash
   git add pages/team.html
   git commit -m "fix: исправить опечатку в описании роли"
   git push
   ```
4. GitHub **автоматически обновит** ваш открытый Pull Request! Преподаватель увидит новый коммит и выполнит **Merge** (слияние).

После того как преподаватель нажмёт кнопку **Merge**, статус вашего PR сменится на фиолетовый значок **Merged** — ваша работа принята! 🎉

## ⚠️ Памятка по частым ошибкам

1. **Ошибка: «fatal: refusing to merge unrelated histories» или случайный коммит в ветку `main`:**
   Перед началом работы всегда проверяйте текущую ветку через `git branch`. Вы должны быть в своей `feature/...` ветке.
2. **Ошибка: попытка отправить `git push upstream main`:**
   У вас нет прав записи в репозиторий преподавателя! Отправлять изменения нужно в `origin`: `git push origin <ваша-ветка>`.
3. **Ошибка: сломались стили или картинки:**
   Убедитесь, что в теге `<link rel="stylesheet">` указан путь `../style.css` с двумя точками, так как ваш файл находится внутри вложенной папки `pages/`.
