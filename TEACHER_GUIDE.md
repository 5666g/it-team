# Методическое руководство для преподавателя

## Практическое занятие: «Командная разработка с использованием Git, GitHub, Pull Request и GitHub Pages»

* **Продолжительность:** 80 минут (1 академическая пара).
* **Целевая аудитория:** группа студентов (~8 человек) с базовыми представлениями о Git, без углублённых знаний HTML/CSS.
* **Формат:** практическая работа с элементами живой демонстрации (Live Demo) и публичного код-ревью в реальном времени.

---

## 🎯 Цели и педагогические задачи занятия

1. **Образовательные:**
   - Закрепить практический навык командного взаимодействия в модели `Fork & Pull Request`.
   - Отработать понимание различий между удалёнными репозиториями `origin` и `upstream`.
   - Освоить культуру изолированных веток (`feature branch`) и понятных коммитов.
   - Продемонстрировать процесс Code Review и непрерывной публикации сайта через GitHub Pages.
2. **Развивающие:**
   - Сформировать понимание открытого цикла разработки (Open Source Workflow).
   - Научить читать замечания ревьюера и досылать исправления в существующий PR.
3. **Воспитательные:**
   - Воспитание ответственности за общее состояние кодовой базы команды.

## 🛠️ Этап 1. Подготовка до начала занятия (чек-лист преподавателя)

Выполните эти действия за 1-2 дня или до звонка:

1. **Создание оригинального репозитория на GitHub:**
   - Войдите в свой аккаунт на GitHub и нажмите **New repository**.
   - Назовите репозиторий, например: `it-team`.
   - Сделайте репозиторий **Public** (обязательно для бесплатной публикации GitHub Pages).
   - **Не** ставьте галочки "Add a README file", так как в проекте уже есть готовые файлы.
2. **Загрузка готовой основы проекта:**
   В папке с проектом выполните инициализацию и публикацию:
   ```bash
   cd it-team
   git init -b main
   git add .
   git commit -m "Initial commit: базовая структура учебного проекта IT Team"
   git remote add origin https://github.com/ВАШ_АККАУНТ/it-team.git
   git push -u origin main
   ```
3. **Настройка GitHub Pages:**
   - Откройте репозиторий в браузере &rarr; вкладка **Settings** &rarr; раздел **Pages** (в левом меню).
   - В блоке **Build and deployment**:
     - Source: `Deploy from a branch`.
     - Branch: `main` / folder: `/ (root)`.
   - Нажмите **Save**.
   - Через 1–2 минуты обновите страницу. Вверху появится ссылка вида:
     `https://ВАШ_АККАУНТ.github.io/it-team/`.
   - Откройте ссылку и убедитесь, что главная страница и все заглушки открываются.
4. **Обновление ссылок в документации:**
   - В файле `README.md` укажите фактические ссылки на ваш репозиторий и опубликованный сайт.
5. **Автоматическое создание GitHub Issues (3 простых способа):**
   В проект уже встроена автоматизация создания всех 8 задач, чтобы не тратить время на ручной ввод:

   * **Способ А (В 1 клик через GitHub Actions — САМЫЙ ПРОСТОЙ, не требует CLI и токенов):**
     1. Загрузите проект на GitHub.
     2. Перейдите во вкладку **Actions** вашего репозитория.
     3. В левой колонке выберите workflow **Setup Lab Issues**.
     4. Нажмите кнопку **Run workflow** &rarr; подтвердите запуск.
     5. Через 5 секунд все 8 Issues будут автоматически созданы со всеми тегами и разметкой!

   * **Способ Б (Через PowerShell / Bash скрипты с GitHub CLI):**
     - Windows (PowerShell): `.\scripts\create_issues.ps1`
     - Linux / macOS (Bash): `./scripts/create_issues.sh`

   * **Способ В (Через Python скрипт без сторонних библиотек):**
     ```bash
     python scripts/create_issues.py --repo ВАШ_АККАУНТ/it-team --token ВАШ_ТОКЕН
     ```

> ⚠️ **Важное замечание по правам доступа:**  
> **Не добавляйте студентов в Collaborators оригинального репозитория!**  
> Смысл лабораторной работы состоит именно в демонстрации работы стороннего контрибьютора через Fork и Pull Request с ограничением прав прямой записи.

00:45 ─── [10 мин] Git commit, push в fork, создание Pull Request
00:55 ─── [15 мин] Живое код-ревью, правки, Merge на проекторе
00:70 ─── [10 мин] Демонстрация живого сайта на GitHub Pages, итоги
00:80 ─── Конец занятия

### Подробное содержание этапов:

#### 1. Вводная часть и постановка задачи (10 минут)
* Показать на проекторе исходный сайт через GitHub Pages:
  - Обратить внимание на то, что сайт полностью работоспособен, но все разделы пока содержат заглушки («Раздел в разработке»).
* Объяснить общую цель группы: за 80 минут совместными усилиями превратить сайт-заглушку в полноценный информационный портал команды IT Team.
* Распределить 8 заданий между присутствующими студентами (по журналу или по желанию).

#### 2. Демонстрация преподавателя у доски / на проекторе (15 минут)
* Показать на экране процесс от лица разработчика:
  1. Нажатие кнопки **Fork**.
  2. Копирование ссылки на свой форк и команда `git clone`.
  3. Команда добавления оригинала: `git remote add upstream <url-преподавателя>`.
  4. Проверка через `git remote -v` и объяснение разницы:
     - `origin` — мой личный репозиторий в облаке (туда я могу писать).
     - `upstream` — репозиторий преподавателя (туда я писать не могу, только читать).
  5. Создание ветки: `git checkout -b feature/team-members`.
* Показать шаблон `pages/template.html` и объяснить, как копировать карточки `<article class="card">` без поломки HTML-структуры.

#### 3. Самостоятельная работа студентов (20 минут)
* Студенты форкают, клонируют проект, создают ветку и редактируют свой HTML-файл.
* Преподаватель циркулирует по аудитории и помогает с типичными затруднениями:
  - Опечатка в ссылке на репозиторий при клонировании.
  - Попытка редактировать файл `index.html` вместо своего в папке `pages/`.
  - Случайно удалённый закрывающий тег `</div>`.
* Проверка локально: студент открывает изменённую страницу в браузере двойным кликом.

#### 4. Фиксация и отправка Pull Request (10 минут)
* Преподаватель напоминает последовательность команд:
  ```bash
  git status
  git diff
  git add pages/<файл>.html
  git commit -m "feat: понятное описание"
  git push -u origin <имя-ветки>
  ```
* Студенты открывают интерфейс GitHub и создают Pull Request.
* Преподаватель акцентирует внимание на правильном выборе базового репозитория (`base repository: преподаватель/it-team`, `base: main`).

#### 5. Публичное код-ревью и слияние (Merge) на проекторе (15 минут)
* Преподаватель выводит на проектор вкладку **Pull requests** оригинального репозитория.
* По очереди разбираются 2-3 входящих PR:
  - Вкладка **Files changed**: демонстрация зелёных/красных строк.
  - Одобрение хорошего оформления.
  - Показ учебной ошибки (например, студент написал неинформативный коммит или оставил заглушку) &rarr; написание комментария в строке кода &rarr; запрос изменений (**Request changes**).
  - Студент вносит правку, делает повторный коммит и `git push` &rarr; PR на экране преподавателя мгновенно обновляется сам.
* Преподаватель нажимает **Merge pull request** &rarr; **Confirm merge**.

#### 6. Демонстрация GitHub Pages и подведение итогов (10 минут)
* Открыть ссылку на GitHub Pages.
* Показать, как после слияния PR сайт автоматически обновился (GitHub Actions выполняет сборку за 30-60 секунд).
* Поздравить группу с успешным командным релизом.
* Ответить на вопросы, выставить оценки/баллы за практическую работу.

## 🔍 Инструкция для преподавателя: Проверка и Merge Pull Request

### Как проверять входящий PR:
1. Перейдите во вкладку **Pull requests** вашего репозитория.
2. Кликните на PR студента (например, `#1 feat: Заполнение страницы участников команды`).
3. Перейдите во вкладку **Files changed** (Изменённые файлы):
   - **Правило 1:** Студент должен был изменить **только один файл** (свой назначенный `pages/<имя>.html`). Если изменены `index.html` или `style.css` — вежливо попросите откатить эти файлы.
   - **Правило 2:** Проверьте целостность HTML-разметки: нет ли оборванных тегов `</article>`, `</div>`.
   - **Правило 3:** Проверьте корректность текста: нет ли нецензурной лексики, приватных личных данных (номеров телефонов, реальных домашних адресов).
4. **Как оставить комментарий:**
   - Наведите курсор на нужную строку в коде, нажмите появившийся синий значок плюса `+`.
   - Напишите замечание и нажмите **Start a review** или **Add single comment**.
5. **Как принять и слить изменения:**
   - Нажмите зелёную кнопку **Review changes** &rarr; выберите **Approve** &rarr; **Submit review**.
   - Вернитесь во вкладку **Conversation** &rarr; нажмите большую зелёную кнопку **Merge pull request** &rarr; **Confirm merge**.

## 👥 Сценарии при неполной посещаемости (пришло 3–5 человек)

В реальном учебном процессе группа редко присутствует в полном составе. Архитектура проекта специально спроектирована под эту ситуацию:

### Почему сайт не сломается?
* Все 8 HTML-страниц существуют в репозитории изначально.
* Ссылки в меню навигации и карточки на главной странице ведут на реальные файлы, а не на несуществующие адреса.
* Если страницу никто не редактировал, посетитель видит аккуратный блок заглушки с иконкой ⏳: «Раздел находится в разработке».

### Варианты ведения занятия при 3–5 студентах:

1. **Вариант «Приоритетные разделы» (Рекомендуемый):**
   Распределите только ключевые страницы:
   * 1-й студент: `pages/team.html` (Команда)
   * 2-й студент: `pages/projects.html` (Проекты)
   * 3-й студент: `pages/technologies.html` (Технологии)
   * 4-й студент: `pages/about.html` (О нас)
   * 5-й студент: `pages/contacts.html` (Контакты)
   Остальные разделы (`achievements.html`, `events.html`, `resources.html`) просто остаются со штатными заглушками до следующего занятия или даются в качестве домашнего задания.

2. **Вариант «Повышенная нагрузка» (для сильных студентов):**
   Студенты, быстро сдавшие свой первый PR, могут взять вторую задачу из оставшихся (например, создать вторую ветку `feature/events-schedule` и открыть второй PR). Это даст отличный опыт работы с несколькими последовательными ветками!

3. **Вариант «Демонстрация преподавателем»:**
   Преподаватель может сам в прямом эфире заполнить один из разделов, показав процесс от своего имени.

## 🚨 Потенциальные проблемы и способы их быстрого решения

| Проблема на занятии | Причина | Быстрое решение преподавателя |
| :--- | :--- | :--- |
| **Студент не может сделать `git push` (Permission denied 403)** | Студент пытается отправить ветку в оригинальный репозиторий преподавателя, а не в свой форк | Проверьте `git remote -v`. Замените URL `origin` на адрес личного форка студента: `git remote set-url origin https://github.com/СТУДЕНТ/it-team.git`. |
| **Студент сделал коммит в ветку `main` вместо `feature/...`** | Забыл создать ветку перед редактированием | Создайте ветку из текущего состояния: `git checkout -b feature/<имя>`. Для возврата локального main: `git branch -f main upstream/main`. |
| **В Pull Request попали чужие или лишние файлы (`index.html`)** | Случайно сохранил изменения в других файлах | Откатить лишние файлы: `git checkout origin/main -- index.html`, затем сделать коммит и push. |
| **Сломалась вёрстка страницы (съехали стили)** | Студент изменил путь к CSS или удалил класс контейнера | Проверьте строку 8 в файле студента: должно быть ровно `<link rel="stylesheet" href="../style.css">` с двумя точками. |
| **GitHub Pages не обновляется после Merge** | Кэш браузера или задержка сборщика GitHub Actions | 1. Нажмите в браузере комбинацию `Ctrl + F5` (или `Cmd + Shift + R`) для очистки кэша.<br>2. Проверьте вкладку **Actions** в репозитории: деплой обычно занимает 40-60 секунд. |
| **Не удаётся клонировать из-за авторизации GitHub в консоли** | У студента не настроен Git Credential Manager или Personal Access Token (PAT) | Предложите войти через GitHub Desktop или использовать расширение GitHub в VS Code (кнопка «Sign in with GitHub»). |
